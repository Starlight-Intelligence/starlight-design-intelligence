# Living design review rubric

Judge the exact artifact and intended task. Keep usefulness, visual craft, operational truth, and commercial learning separate. The presence of a rubric does not certify downstream adoption.

## Critical gates

| Gate | Passing evidence | Blocking defect |
| --- | --- | --- |
| Identity | Inspected source, stable IDs, explicit candidate/accepted state | A new rendition is presented as approved canon |
| User task | Complete useful output and a clear next decision | Character spectacle obscures the work |
| Contract integrity | Valid references, distinct role/character/runtime IDs | Missing dependencies, cycles, or narrative authority escalation |
| State truth | Data-backed status, source/freshness, recoverable failures | Fake online state, invented progress, or unsupported completion |
| Access | Server-enforced tenant and permission boundaries where implemented | UI filtering or personality prose treated as authorization |
| Provenance | Traceable assets, source revisions, derivative and audience state | Private material exposed or rights inferred from generation |
| Accessibility | Keyboard, names, focus, contrast, reflow, reduced motion | An essential action depends on color, motion, image, or pointer |
| Recovery | Useful work retained and safe next action | Blind duplicate execution, lost work, or a misleading retry |

A failed critical gate blocks the corresponding release claim. Cosmetic scores cannot compensate.

## Visual assessment

Inspect the character at avatar and scene sizes. Ask whether the silhouette, face, and functional feature remain recognizable; whether material boundaries are coherent; whether a role can be inferred without a large explanation; and whether light, crop, props, and texture support the selected family.

Inspect the UI in its chosen surface mode. The primary task, artifact, and next action should be evident before the decorative environment. Check text measure, contrast against the actual substrate, spacing, component consistency, focus, and mobile hierarchy. Keep authored glasswork in imagery or restrained accents while controls stay readable.

For generated artwork, inspect the actual export for malformed anatomy, accidental text/marks, broken reflections, identity drift, and unsuitable cropping. Apply the repository's generated-asset gate. A prompt, hash, or attractive thumbnail is not proof of final visual quality.

## Behavioral assessment

Test normal assistance, uncertainty, failure, cancellation, and return visits. The personality should remain consistent while state information remains precise. A companion may be warm and playful; it must not conceal uncertainty, overstate memory, pretend to be conscious, or pressure a user to maintain a relationship.

Review each skill for a precise trigger, required inputs, a bounded workflow, useful output, missing-capability behavior, and acceptance example. A portable workflow must remain useful without a new server or hidden dependency.

## Minimum fixtures

1. Select a character and inspect its family, role, skills, playbooks, and connectors.
2. Compile valid contracts and confirm a deterministic projection.
3. Reject a missing reference or cyclic design ancestry.
4. Preserve unknown status when there is no runtime binding.
5. Reject or visibly report malformed, revoked, unauthorized, or stale runtime input where that adapter exists.
6. Complete the UI's main selection/inspection path with keyboard and narrow layout where a UI is provided.
7. Verify private assets and identifiers do not cross into a public export.

Only report fixtures actually executed. Mark an unimplemented adapter's runtime fixture as not applicable to the skills-only package, with integration work explicitly pending.

## Receipt

Record artifact/source revision, package hash, source references, evaluated journey, executed commands or observations, defects repaired, remaining limitations, reviewer identity, and separate statuses for built, tested, account-saved, installed, runtime-tested, merged, deployed, and customer-accepted.

Use an independent reviewer for substantive release work when available. Provide the actual files and intended journey, not the desired verdict. If only self-review is possible, name it. Public identity acceptance and production promotion remain with the authorized owner.

## Suggested pilot

Use Nacre, Helix, and Orin for one research-to-review task. Give participants the same source material and ask them to find the responsible role, inspect its access, obtain the artifact, and recover from an unavailable source. Compare with the existing product. Record errors and useful outcomes; do not infer adoption from internal package tests.
